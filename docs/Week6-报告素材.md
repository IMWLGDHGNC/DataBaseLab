# 第二阶段 v1.0 报告素材：第六周

## 设计思路

我们以第五周已核对的完整 ER 模型、数据字典、问题清单及第三、四周 SQL 为输入，逐表审查主码、候选码、函数依赖和更新异常。现有 15 张业务表已将类别与商品、订单与明细、采购与批次、销售与支付/积分流水按不同事实分开；销售明细保存历史成交价。没有发现需要全面拆表才能解决的普遍 1NF、2NF 或 3NF 问题，因而保留主体结构。

本次选择减少库存流水的条件性重复来源：`InventoryMovement.PurchaseItemID` 可由 `BatchID` 沿 `InventoryBatch.PurchaseItemID` 唯一还原。v0.1 的复合外键已保证两处一致；v1.0 删除流水重复列、相关外键和供复合外键引用的非最小超码约束。采购来源仍可沿“流水 → 批次 → 采购明细 → 采购单”追溯。`SalesOrder.TotalAmount`、`InventoryBatch.OnHandQty`、`Customer.PointsBalance` 属于保留的跨表缓存，须由受控事务同步维护并定期对账。

删除流水重复列后，批次的采购来源若可被改写，历史流水也会被错误重解释。迁移因此增加一个更新触发器：有库存流水的批次不能更换 `PurchaseItemID`；回归实际验证错误 51620。

## 实验过程与结果

`sql/week6/migration.sql` 检查 15 表 46 行、原有约束、采购来源匹配、订单/库存/积分余额后，在单一事务中更改字段和约束；将每条库存流水及批次可还原的来源做迁移前后双向比较，失败即回滚。`sql/week6/regression.sql` 检查目标目录、行数、销售额、订单金额、库存与积分余额、合法写入回滚、非法外键和数量拒绝，以及角色访问边界。

2026-10-10 在课程服务器现有 SQL Server 2022 Docker 容器里，新建独立库 `DataBaseLab_Week6_20261010113646`。从原脚本重建 v0.1 后，先运行第四周 34 项权限及第五周目录/边界检查，得到 15 表、107 属性、25 外键、46 行与 9 项探针通过。迁移返回 `W6_MIGRATION_PASS`：15 表 46 行、库存流水 6 行。迁移后目录为 106 属性、23 外键、9 项 UNIQUE；再次通过 34 项权限，回归得到已完成销售 15 件、64.50 元，订单/库存/积分对账一致，合法、非法及越权用例符合预期，最终 `W6_REGRESSION_PASS`、`WEEK6_SERVER_PASS`。完整输出见[第六周结果](../result/week6/README.md)。

服务器 `sqlcmd` 初次未启用 `QUOTED_IDENTIFIER`，在建表阶段停止；随后使用 `-I` 在全新独立库完成整轮。失败的空库经确认无业务表后已清理，成功测试库保留供复核；正式库没有参与迁移。服务器脚本将原始 transcript 留在被忽略的 `output/week6/`；公开日志经过账户、地址、路径和凭据检查。本机未运行数据库。

## 实验总结与审核边界

本次设计只减少一个可以由批次稳定追溯的来源列，保留 15 张业务表、订单与库存业务事实及历史数据。独立样例库的自动验证已通过，不能由此推断真实业务库已迁移，也不能代替组员对候选码假设、冗余取舍和 SQL 的逐项人工审查。正式迁移决定与人工反馈应在后续阶段报告中单独记录。
