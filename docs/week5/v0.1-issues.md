# v0.1 问题与改进清单

本周依据 ER 模型审查已有结构，不直接重建 v0.1。证据来自第一、二周业务约定、第三、四周 SQL、样例和本周回滚探针。以下改进是下一阶段的设计输入，尚未实施，也未把它们当成已经完成的规范化结论。

| 编号 | 问题与业务证据 | 影响 | 改进方向与安排 |
| --- | --- | --- | --- |
| Q01 | 采购单、销售单业务上至少有一条明细，但父表可独立插入；本周探针中的空单被数据库接受。04-verify 仅检查销售明细存在性 | 结构允许不完整订单；不能用 FK 声称完全参与已实现 | 第6周明确持久化边界与迁移前坏数据检查；第7—9周整单创建事务同时写入头、明细和锁定，失败全回滚；采购复核补上明细存在性 |
| Q02 | 销售明细虽有独立 SalesItemID，仍有 `(SalesOrderID, ProductID)` UNIQUE；重复 SKU 探针返回 2627。现有业务把一单同 SKU 合并；讲解提示不能默认所有业务都只出现一行 | 将来同商品不同价格、赠品或促销拆行无法表达，不能将当前唯一约束推广为通用规则 | 保留 v0.1 已确认合并语义；第6周先确定拆行需求，如需要再删除组合唯一约束并评估行号、统计、锁定及回归；不能仅为匹配讲解就无依据改表 |
| Q03 | OnHandQty、PointsBalance、TotalAmount 保存合计，与库存／积分流水及订单明细重复表达；本周将 B00 现存量加 1 可通过本行 CHECK | 更新异常；任意写入可能产生账实不符，单表非负不能保证聚合一致 | 第6周分析函数依赖和存储合计的取舍，保留则指定唯一维护入口；第7—9周通过事务维护多表并验证并发，保留对账查询 |
| Q04 | InventoryReservation 的 SalesItemID 与 BatchID 分别合法，但外码不保证它们属于同一 SKU；本周跨商品锁定可插入 | 给错误商品占用库存；合计超量也不能由本行 CHECK 拦截 | 第6周比较增加受约束的 SKU 配对字段、触发器或受控事务方案，记录冗余与维护代价；应用入口统一验证商品和可售量并保护并发 |
| Q05 | 支付只有成功次数和正金额的数据库限制；本周把待出库 ST02 的成功支付金额改为 1 元可通过约束；状态字段可以直接更新 | 金额、支付期限与状态迁移可脱节 | 第6周列出状态机和金额一致性不变量；第7—9周受控支付接口验证旧状态、金额、有效期，配合幂等流水号和事务；真实支付仍不在当前范围 |
| Q06 | PointsMovement 有订单顾客配对和每单唯一，但无法由外码判定订单完成与会员资格；Customer.IsMember / JoinedAt 仅保存当前身份 | 历史会员规则可能被当前资料修改破坏；未来退会、重复入会无法追溯 | 第6周决定会员身份是否可变；若支持变化，评估会员资格历史与赠分事实快照，再制定迁移；不因“会员”一词机械新增会员表 |
| Q07 | PurchaseOrder.CreatedBy / ApprovedBy / ReceivedBy 引用 Employee，但不限制岗位或在职状态；数据库测试角色与 Employee.Position 没有绑定 | 可用错误岗位员工做业务经办；图上员工关系不能充当权限控制 | 保留三种经办联系；第7—9周建立应用账号与员工／角色映射，验证岗位和在职状态，使用最小权限数据库账号 |
| Q08 | Customer.AccountName 是账号字段；第四周升级已实现四个员工角色及顾客/会员两个角色，CustomerPrincipal 映射和受控过程可只读本人订单/积分，但 WITHOUT LOGIN 用户仅供测试，没有应用认证及业务写入入口 | 本人只读隔离已由 34 项权限案例验证；v0.1 仍不能直接称为可登录应用 | 第7—9周设计应用认证与真实账号映射、密码哈希或受信身份方案、参数化查询和服务端授权，沿用并扩展现有隔离；敏感凭据不进入 Git |
| Q09 | OrderException.HandledBy 和 HandlingNote 可被更新，只有 RecordedAt；EX00 / EX01 分别表示两个原因，没有独立处理动作实体 | 一条异常的多次处理时间、经办人及意见可能被覆盖 | 第6周确认是否需要审计历史；需要时引入异常处理事件并设计回填策略，保留异常记录及原始事实 |
| Q10 | InventoryBatch 的批号唯一范围为 `(PurchaseItemID, SupplierBatchNo)`，批次身份与采购行绑定；相同厂家批号跨采购单可能形成多个内部批次 | 内部到货批次与厂家生产批次容易混淆；召回需跨行查询 | 本周明确 BatchID 是内部库存批次。第6周先验证召回需求，再评估厂家生产批次实体；保留到货来源，不能全局唯一 SupplierBatchNo |
| Q11 | Product 的 `(Brand, ProductName, Specification, SaleUnit)` 是当前候选码，名称变化可能影响业务识别；SupplierName、EmployeeName、CustomerName 均非唯一 | 新品牌命名、包装或 SKU 编码策略变化可能引入标识冲突；姓名不能作为实体标识 | 保留独立编号和当前已实现唯一约束；第6周确认真实 SKU 编码、条码是否稳定，必要时设计替代码及迁移冲突检查 |
| Q12 | 当前只有成功／失败支付样例；没有取消订单、跨批次分配、重新锁定、多次失败支付等完整样例 | 图中 0..N／M:N 虽由业务和模式支持，但样例覆盖不足，应用测试容易遗漏分支 | 本周用回滚探针证明支付可多次失败、锁定组合可多次出现；第6周迁移回归与第7—9周集成测试再补贯通场景，不改原 46 行基线 |

## 保留与延期

保留商品、类别、供应商、员工、顾客，以及采购／销售订单头与明细；保留历史成交价与收货快照；保留批次、锁定、实物流转和积分事件的分离。快照记录当时事实，与当前商品价／顾客资料语义不同，不能仅因数值重复就删除。会员当前使用顾客属性，供应商无需登录，单店单仓无需先加仓库表。

第6周再决定规范化分解、必要冗余及迁移方案。第7—9周落实登录、岗位与顾客权限、参数化访问、整单事务、并发控制和异常处理。退款、退货、物流轨迹、积分兑换仍在当前业务边界之外。

所有“探针接受”均表示发现现有约束缺口，不是业务规则正确；探针事务均回滚。自动核对不能替代学生的业务判断。实际职责见[组内分工](../../组内分工.md)；2026-10-01 用户授权修复 review 问题后合并；未新增学生逐项人工验收结论。
